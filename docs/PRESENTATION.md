## 1. 프로젝트 기획 개요

**서비스명**: 상속자들 (`inheritors-web`)

**한 줄 정의**: 시니어 자산가 대상 유언대용신탁 특약·세금 안내 + 법률 판례 RAG 챗봇

**목적**
- 시니어 자산가를 위한 유언대용신탁 시뮬레이션 + MCP 기반 실시간
  법원 판례 RAG 챗봇 제공


**MVP 기능 범위**

| 구분 | 기능 | 상태 |
|---|---|---|
| Core | 법률/판례 RAG 대화형 챗봇 (`/chat`) | ✅ 구현 |
| Core | korean-law-mcp 연동 — 실시간 판례/법령 검색 | ✅ 구현 |
| Core | Quick 버튼(판례/신탁 내용/맞춤 상담) | ✅ 구현 |
| Core | 6턴 이상 상담 시 자동 요약 리포트 | ✅ 구현 |
| Support | 온보딩 화면 | ✅ 구현 |
| Support | 시니어 맞춤 글자 크기 조절 | ✅ 구현 |
| Post | 3단계 자산승계 시뮬레이션(원안) | 채팅 기반 리포트로 대체 |
| Post | 공시가격 자동 산정 & PDF 다운로드 | 백로그 |

## 3. 시연 및 설명

### 3.1 핵심 플로우

```
온보딩(/) → 챗봇 상담(/chat) → [6턴 이상 시 배너] → 상담 리포트(/report)
```

### 3.2 실제 데모 대화 (박정호 페르소나, 9턴 · `/chat` 실호출 결과)

> `docs/demo-dialogue.md` — 지어낸 답변 없음, 실제 DB 문서(설명서/계약서/상속증여세) 검색
> 결과를 근거로 생성된 실답변 그대로.
```text
사용자:

제가 사망한 뒤에도 딸이 성인이 될 때까지 집을 안전하게 신탁에 맡겨두었다가, 일정한 나이가 되면 딸 명의로 이전되도록 할 수 있나요?

상속자들:

네, 가능합니다. 유언대용신탁을 통해 사망 후에도 자녀가 성인이 될 때까지 재산을 안전하게 관리하고, 성년이 되는 시점에 신탁재산을 자녀 명의로 이전할 수 있습니다. 자녀가 성인이 될 때까지 재산이 안전하게 관리되며, 성년이 되면 자동으로 재산이 이전됩니다. 이는 사전 상속설계의 일환으로, 생활비 분할 지급이나 특정 시점 재산 승계 등 다양한 맞춤형 설계가 가능합니다.

사용자:

이혼해서 지금은 딸과 제가 같이 살고 있고, 부모님과 미혼 남동생도 함께 살고 있습니다. 이렇게 가족 구성이 복잡한 경우에도 집만 따로 딸에게 지정하는 것이 부모님이나 남동생과의 유산분할 분쟁으로 번질 수 있나요?

상속자들:

유언대용신탁을 통해 특정 재산을 딸에게 지정할 수 있지만, 유류분 권리는 침해할 수 없습니다. 부모님이나 남동생이 유류분 반환청구를 할 수 있으며, 이 경우 신탁재산 관련 분쟁이 발생할 수 있습니다. 유언대용신탁을 설정하더라도 유류분 관련 소송 가능성을 염두에 두어야 합니다.

사용자:

그럼 부모님과 남동생의 유류분 침해 문제를 최대한 줄이려면 어떻게 신탁을 설계하는 게 좋을까요? 예를 들면 신탁 계약 시 부모님과 남동생에게도 일부 금전을 배분하는 방식으로 미리 조정해두는 게 도움이 될까요?

상속자들:

부모님과 남동생에게도 일부 금전을 배분하는 방식으로 미리 조정해두는 것은 유류분 침해 문제를 줄이는 데 도움이 될 수 있습니다. 신탁 계약 시 상속인들의 유류분을 고려해 재산을 배분하고 충분히 협의하여 동의를 얻는 것이 중요하며, 계약서에 명확한 조항을 포함시키고 법률·세무 전문가의 자문을 받는 것이 좋습니다.

사용자:

만약 제 건강 상태가 달라지거나 가족 상황이 바뀌면, 이미 체결한 유언대용신탁 계약을 나중에 수정하거나 해지할 수 있나요?

상속자들:

유언대용신탁 계약은 위탁자가 기간 만료 전에 해지할 수 있습니다. 다만 운용자산(부동산 제외)을 모두 매도해야 해 자금 수령까지 수일이 걸릴 수 있고, 중도해지수수료가 가입 기간에 따라 차등 부과됩니다. 약관 변경 시 위탁자에게 불리한 내용은 사전 통지되며, 동의하지 않으면 계약을 해지할 수 있습니다.

사용자:

유언대용신탁을 설정하고 유지하는 데 드는 비용이나 수수료는 대략 어느 정도인가요?

상속자들:

비용은 기본보수와 집행보수로 나뉩니다. 기본보수는 계약 체결·유지 비용으로 예를 들어 금전 신탁원본의 0.5%(최소 500만 원) 수준이며, 집행보수는 사망 후 재산 승계 시 드는 비용으로 신탁재산가액 10억 원 이하일 경우 1.0% 등 구간별로 차등 적용됩니다. 신탁재산 종류·금액에 따라 협의로 조정될 수 있습니다.

사용자:

마지막으로, 나중에 딸이 성인이 되어 신탁되어 있던 집을 이전받을 때 내야 하는 상속세나 증여세는 어떻게 계산되나요?

상속자들:

신탁재산이 상속재산으로 간주되면 상속세가 부과될 수 있으며, 상속재산가액엔 신탁재산의 공정가액이 포함되어 계산됩니다. 재산을 우회적으로 받은 것으로 볼 수 있는 경우에는 증여세가 과세될 수도 있습니다. 구체적인 세금 계산은 세무 전문가와 상담하는 것이 좋습니다.
```
### 3.3 그 밖의 시연 포인트

- **Quick 버튼**: 타이핑이 서툰 시니어를 위해 판례 조회/신탁 내용 검색/맞춤 상담 신청 3개를
  버튼 클릭만으로 즉시 조회
- **참고 문서 카드**: 답변 근거가 된 문서/판례를 접기/펼치기(`<details>`)로 노출 — 길게
  펼쳐지지 않도록 기본은 접힘, 클릭 시 전체 목록
- **MCP 호출 표시**: "korean-law-mcp를 호출했습니다" + 호출 이유(검색어)를 답변 아래 투명하게 노출
- **6턴 자동 리포트**: 상담이 쌓이면 배너로 리포트 안내 → 지금까지 대화에서 언급된 자산/리스크를 LLM이 요약 (지어내지 않음, 대화에 없는 항목은 빈 배열)
- **글자 크기 조절**: 상단바에서 100~150% 조절 — 시니어 접근성

## 4. 적용한 기술

### 4.1 스택 개요

| 영역 | 기술 |
|---|---|
| Frontend | Next.js 14 (App Router), React 18, TypeScript, Tailwind CSS 3.4 |
| Backend | FastAPI, SQLAlchemy 2, Pydantic 2 |
| DB | PostgreSQL + pgvector (Supabase) |
| LLM (프로덕션) | OpenAI API (`gpt-4o-mini`) |
| 임베딩 | `BAAI/bge-m3` (다국어, 1024차원, `sentence-transformers`) |
| RAG | LangChain (`langchain-core`, `langchain-openai`) |
| 외부 법률 API | korean-law-mcp (MCP, stdio JSON-RPC) |

### 4.2 RAG 파이프라인

```
질의 → bge-m3 임베딩 → pgvector 코사인 유사도 검색
     (설명서/계약서/상속증여세 카테고리별 균형 검색 + 은행·신탁유형 메타데이터 필터)
     + korean-law-mcp/lexguard-mcp 판례·법령 실시간 검색 (LLM이 호출 필요성 판단)
     → 컨텍스트 조립 → LLM 스트리밍 응답
```

- **데이터**: 문서 12건(설명서 4 / 계약서 5 / 상속증여세 3), 청크 209건, 전량 임베딩 적재
- **카테고리별 균형 검색**: 단일 top-k 검색 시 한 카테고리가 결과를 독식하는 문제 →
  설명서/계약서/상속증여세 각각 top-k를 따로 조회해 합침
- **은행/신탁유형 메타데이터 필터**: "KB국민은행에서는?" 같은 질문에 벡터 검색 + 구조화
  필터를 결합해 정확히 해당 은행 문서만 검색
- **no-context 임계값(0.5)**: 유사도가 낮으면 LLM 호출 자체를 생략하고 "자료를 찾지 못했다"
  고정 응답 — 근거 없는 답변을 검색 단계에서 차단하는 1차 환각 방지

### 4.3 MCP(Model Context Protocol) 연동

- **korean-law-mcp**: 법제처/법원 판례 데이터를 stdio JSON-RPC로 호출하는 오픈소스 MCP
  서버. FastAPI 수명 동안 프로세스 하나를 유지해 호출마다 재기동 비용을 없앰
- **LLM 기반 tool-calling**: "이 질문에 판례/법령 검색이 필요한가?"를 고정 키워드가 아니라
  LLM(`gpt-4o-mini`)이 질문 의미를 보고 직접 판단 — 도구 선택, 검색어 생성까지 LLM이 수행

## 5. 프로젝트 설계 및 관리

### 5.1 아키텍처

```
apps/web (Next.js)  →  apps/api (FastAPI)  →  packages/rag (LangChain)
                                            ↘  mcp_client.py (korean-law-mcp)
                                           
                     →  PostgreSQL + pgvector (Supabase)
```

- **모노레포 구성**: `apps/{web,api}` + `packages/{rag,legal-mcp,shared-types}` — npm
  workspaces + Turborepo


### 5.2 DB 스키마 (PostgreSQL + pgvector)

| 테이블 | 역할 |
|---|---|
| `documents` / `chunks` | RAG 원본 문서 + 청크 임베딩(`VECTOR(1024)`) |
| `chat_sessions` / `chat_messages` | 상담 세션 및 대화 기록 |
| `message_sources` | 답변별 근거 문서/판례(score, rank 포함) — 추천 로직 근거 데이터로도 활용 |

### 5.3 이슈 기반 개발

- 기능 단위 ISSUE 작성(`.github/ISSUE_TEMPLATE/`) → `feat/{기능명}` 브랜치 → PR → `staging`
  머지 순서로 진행
- `docs/issue/`에 기능별 스펙 문서화(FN-CORE-01~05, FN-SUPP-01~02)
- 진행 상황은 `docs/PLAN.md`에 지속 갱신, RAG 실측 결과는 `docs/RAG.md`에 별도 기록

### 5.4 실측 기반 개발 문화

이 프로젝트 전반에 걸쳐 "실측 확인" 없이 넘어간 결정이 거의 없음 — 예:
- 유사도 임계값(0.5)은 관련/무관 질의 11개 표본 실측으로 도출
- korean-law-mcp 연동 실패 원인(POSIX `shell=True` 버그)을 로그로 직접 추적해 수정
- Docker 이미지 용량 문제(5.5GB)를 pip 설치 로그에서 직접 원인(CUDA 패키지) 확인 후 해결

### 5.5 프로젝트 규모 (git 실측)

- 총 커밋 99건, 병합 PR 31건, 기여자 5명
- 브랜치 전략: `main`(배포) ← `staging`(통합) ← `feat/*`(기능 단위)

## 6. 협업 방법

### 6.1 브랜치 전략

```
main
 └─ staging   (개발 통합 브랜치)
     └─ feat/{기능명}  (기능 단위 작업 브랜치)
```

- `main`에는 직접 push/PR 금지 — 모든 작업은 `staging`을 거침
- 브랜치는 기능 단위로 생성, 하나의 브랜치에 여러 기능을 섞지 않음
- 작업 시작 전 + 재개 시마다 `staging`을 rebase해 최신 상태 유지, 충돌은 AI 자동 처리 없이
  직접 파일 열어 해결

### 6.2 커밋/PR 컨벤션

- 커밋: `type: 작업 내용` (`feat`/`fix`/`chore`/`docs`/`refactor`/`test`), TASK 단위로 작게 분리
- PR: ISSUE 연결 + `PULL_REQUEST_TEMPLATE.md` 양식(작업 내용/배경/변경사항/체크리스트)에 맞춰 작성
- **merge 방식은 squash merge로 통일** — `staging` 히스토리를 깔끔하게 유지

### 6.3 코드 리뷰

- PR은 최소 1인 이상의 approve 후 merge
- 작성자 본인은 본인 PR을 approve/merge하지 않음
- 프론트/백엔드 작업은 각각 ISSUE 생성 + `front`/`back` 라벨

## 7. Q&A (예상 질문 대비)

| 예상 질문 | 답변 포인트 |
|---|---|
| 왜 자체 LLM(Ollama)이 아니라 OpenAI로 갔나요? | 10.8B 양자화 모델의 지시 준수가 불완전(시스템 프롬프트를 스스로 읊는 등) — 실측 재현 확인 후 프로덕션은 OpenAI로 전환, Ollama 경로는 `/prototype/chat`으로 보존 |
