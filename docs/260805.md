# 2026-08-05 작업 회고 — Ollama 셀프호스팅 → OpenAI API 전환

하루 동안 진행한 Ollama 운영/MCP 연동 작업 전체와, 그 경험을 바탕으로 OpenAI API로
전환하며 드러난 한계점을 정리한다. 관련 PR: #18~#23(대략), 이슈: [FN-CORE-05](./issue/FN-CORE-05-openai-rag-migration.md).

## 1. Ollama 사용 내역

### 1.1 로컬 개발 환경 구축
- `ollama serve` + `ollama pull hf.co/gchrisoh/EEVE-Korean-Instruct-10.8B-v1.0-Q4_K_M-GGUF`
  (약 6.5GB, Q4 양자화)로 로컬 개발 환경 구성
- `packages/rag/chains.py`에서 `langchain_ollama.ChatOllama`로 연동, 콜드 로드 방지를 위해
  `keep_alive=-1`로 상시 메모리 상주, FastAPI `lifespan`에서 기동 시 `warm_up()` 1회 호출

### 1.2 스트리밍 버그 수정
- `/chat` 호출 시 브라우저에 `ERR_INCOMPLETE_CHUNKED_ENCODING` 발생 — 원인은 Ollama
  모델이 아예 설치 안 돼 있어서 스트림 중간에 예외가 나고, 응답이 끝맺음 없이 끊기던 것.
  `chat_router.py`(현 `chat_shared.py`)의 SSE 스트림 루프를 try/except로 감싸 예외 시
  안내 메시지로 스트림을 정상 종료하도록 수정

### 1.3 답변 페이싱 + 이어쓰기
- 답변이 한 번에 길게 쏟아져 읽기 피로도가 크다는 피드백 → 문장이 끝나는 지점(마침표)에서
  **LLM 생성 자체를 중단**하고 `"더 설명해드릴까요?"`를 붙이는 방식으로 응답 시간 단축
- `POST /chat/continue` 신설 — 재검색 없이 `message_sources`에 저장된 근거를 재사용하고
  이전 답변을 `AIMessage`로 대화 맥락에 넣어 LangChain으로 자연스럽게 이어쓰기

### 1.4 답변 품질 한계 (양자화 모델의 근본적 문제)
- 10.8B 양자화 모델이 시스템 프롬프트 지시를 안정적으로 따르지 않음 — 실측 확인된 증상:
  - 인사말 대신 시스템 지침 자체를 그대로 읊음
  - 사용자 질문을 `[질문] ...`처럼 그대로 반복한 뒤에야 답변 시작
  - `"신뢰도: 90%"` 같은, 프롬프트로 명시적으로 금지한 문구를 계속 붙임(답변 앞/뒤 모두)
    → 후처리로 스트림 앞/뒤를 지연 버퍼링해 결정적으로 제거하는 방어 코드까지 추가했으나
    **중간에 삽입되는 경우는 여전히 못 잡음** (실측 재현됨)
  - 판례 설명 시 사건번호/법원명 나열만 하고 실제 판단 이유를 설명 못 함 → MCP
    `get_decision_text`로 본문을 추가로 받아와 컨텍스트를 보강하고 나서야 개선
- 프롬프트 보정으로 일부 완화했지만 **완전히 해결되지 않음** — 모델 자체의 지시 준수
  능력 한계이며, 온디바이스 양자화 모델의 근본적인 트레이드오프

### 1.5 Docker화 및 배포 시도
- `infra/ollama/Dockerfile`: 모델을 이미지 레이어에 미리 구워 넣어 컴퓨터마다 재다운로드
  불필요하게 함, Docker Hub(`popopododo/inheritors-ollama`)에 push
- **이미지 크기 문제**: `ollama/ollama` 베이스 이미지 자체가 CUDA/Jetpack GPU 백엔드를
  통째로 포함(~3.5GB, 실측) — CPU 전용 배포(AWS Graviton/t4g) 대상에는 전부 죽은 용량.
  멀티스테이지 빌드로 제거해 10.7GB → 6.45GB로 경량화
- **EC2 배포 시 RAM 부족으로 실패**: 후보 인스턴스(t4g.nano, RAM 0.5GB)에 배포하니
  컨테이너가 뜨자마자 OOM으로 죽음 — 실측 에러:
  ```
  ggml_aligned_malloc: insufficient memory (attempted to allocate 6118.50 MB)
  ```
  이미지를 아무리 줄여도 **모델 자체(6.5GB)가 요구하는 런타임 메모리**는 줄지 않아서,
  최소 8GB+ RAM 인스턴스가 필요 — 디스크 최적화와 RAM 요구량은 별개 문제였음
- nginx 리버스 프록시 설정(`infra/nginx/ollama.conf`) 작성 — 스트리밍 응답 특성상
  `proxy_buffering off` 필수, 응답 생성이 오래 걸릴 수 있어 타임아웃 300s로 상향.
  Ollama API에 인증이 없어 컨테이너 포트를 루프백 전용으로 좁히고 보안그룹으로 접근 제한

### 1.6 종합 평가
로컬 개발/프로토타입용으로는 문제없이 동작했지만, **운영 배포 관점에서는 모델 크기 대비
요구 리소스(RAM/디스크)가 소형 인스턴스에 부담스러웠고**, 응답 품질도 양자화 모델의
지시 준수 불완전 문제로 프로덕션에 그대로 내보내기엔 불안정했다.

## 2. korean-law-mcp 개발 내역

### 2.1 초기 상태 — 항상 실패
`mcp_client.py`가 판례/법령 검색을 시도할 때마다 조용히 실패(타임아웃 폴백만 반환)하고
있었음. 근본 원인 2가지를 실측으로 확인:
1. `korean-law-mcp` npm 패키지가 애초에 전역 설치돼 있지 않았음
2. `_resolve_script_path()`의 `subprocess.run(["npm","root","-g"], shell=True)` 버그 —
   POSIX에서 `shell=True` + 리스트 인자를 같이 쓰면 셸이 첫 인자(`npm`)만 명령으로 실행하고
   나머지(`root`, `-g`)는 버림 → 스크립트 경로를 못 찾아 빈 인자로 `node ""`를 spawn

### 2.2 수정 및 구조 개선
- 위 두 버그 수정 후 실제 법제처 Open API 기반 검색 결과가 정상적으로 나오는 것 확인
- 호출마다 새 node 프로세스를 spawn+kill하던 구조 → **FastAPI 수명 동안 유지되는 단일
  프로세스**로 전환 (`main.py` lifespan에서 `start()`/`aclose()`). korean-law-mcp는
  pdfjs/onnxruntime/sharp 등 무거운 의존성 때문에 콜드 기동에만 1~2초 걸림(실측) —
  매 호출마다 이 비용을 물면 라우터의 3초 타임아웃에 걸릴 위험이 있어, 서버 시작 시
  1회만 비용을 지불하도록 개선. 웜 호출은 1~2초 내로 단축

### 2.3 판례 설명 품질 개선
- `search_decisions`가 반환하는 건 사건번호/법원/선고일 같은 검색 결과 "목록"일 뿐,
  판결 이유(실제 내용) 자체가 없어서 LLM이 스토리텔링할 재료가 없었음
- `get_decision_text` 도구(판시사항/판결요지 조회)를 추가로 호출해 최상위 1건의 본문까지
  받아오도록 개선, 시스템 프롬프트에도 "사건번호 나열 대신 이야기하듯 설명" 지시 추가
- 개선 후 실제 판단 이유(예: 유류분 산정 시 재산 가치 평가 기준 시점 등)가 답변에 반영됨

### 2.4 종합 평가
MCP 자체는 안정적으로 동작했고, provider(Ollama/OpenAI)와 무관한 검색/컨텍스트 조립
로직으로 잘 분리되어 있어 이번 OpenAI 전환 시에도 **코드 변경 없이 그대로 재사용**됐다.

## 3. OpenAI API 전환에서 드러난 한계점 / 트레이드오프

`/chat`을 OpenAI API(`gpt-4o-mini`)로, 기존 Ollama는 `/prototype/chat`으로 분리해서
같은 RAG 파이프라인(검색·MCP·프롬프트 조립)에 LLM만 바꿔 끼우는 구조로 전환했다
(`packages/rag/chains.py`의 `llm` 주입 파라미터화). 전환하며 확인된 것들:

### 3.1 얻은 것
- **답변 품질이 명확히 개선됨**: 시스템 지침을 스스로 읊거나 질문을 반복하는 문제,
  `"신뢰도: N%"`를 계속 붙이는 문제 등 Ollama 양자화 모델에서 반복 관찰되던 증상이
  실측 테스트에서 재현되지 않음 — 지시 준수가 훨씬 안정적
- **인프라 부담 해소**: 모델 파일 관리, RAM/GPU 사이징, Docker 이미지 크기 문제가
  전부 사라짐 — 서버는 API 키만 있으면 됨

### 3.2 새로 생긴 한계 / 리스크
- **비용 발생**: Ollama는 로컬 컴퓨팅이라 무료였지만 OpenAI는 토큰당 과금. 사용량이
  늘면 비용이 선형으로 증가 — 트래픽이 예측 안 되는 초기 단계에서는 비용 관리 부담
- **외부 의존성**: 인터넷 연결이 항상 필요하고, OpenAI 측 장애/레이트리밋/응답 지연에
  서비스 가용성이 그대로 노출됨. Ollama는 완전 오프라인 자체 호스팅이 가능했음
- **데이터 프라이버시**: 신탁 상품 상담, 개인 상속 관련 질의가 외부(OpenAI) 서버로
  전송됨 — 민감한 자산/가족 정보가 포함될 수 있는 도메인이라 데이터 처리 정책 검토 필요.
  Ollama는 완전 자체 호스팅이라 데이터가 외부로 나가지 않았음
- **설정 실수 여지**: `.env`에 실제 API 키를 넣어야 하는데, 이번에도 `OPENAI_API_KEY`가
  아닌 `OPEN_API`로 잘못 등록했다가 재확인하는 해프닝이 있었음 — 키 유출/오설정 시
  과금 남용으로 이어질 수 있어 Ollama 대비 운영 관리 포인트가 하나 늘어남
- **재현성/버전 관리**: OpenAI가 모델을 업데이트하거나 특정 모델을 폐지하면 동일한
  응답을 보장하기 어려움. Ollama는 로컬에 고정된 모델 파일이라 버전을 완전히 통제할 수
  있었던 반면, OpenAI는 그 통제권을 벤더에 넘기게 됨

### 3.3 결론
초기 개발/검증 단계에서는 Ollama 셀프호스팅으로 비용 없이 빠르게 검증했고, 그 과정에서
겪은 배포/품질 문제(RAM 부족, 지시 준수 불완전)가 OpenAI API 전환의 실질적인 동기가
됐다. 다만 전환이 무조건적인 개선은 아니고, 비용/외부 의존성/데이터 프라이버시라는
새로운 트레이드오프를 안게 된 것이므로, `/prototype/chat`(Ollama)을 그대로 남겨둬
두 방식을 비교하거나 필요 시 롤백할 수 있게 했다.
