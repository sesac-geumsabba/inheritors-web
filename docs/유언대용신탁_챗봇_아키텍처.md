# 유언대용신탁 자산승계 설계 챗봇 — 브랜치 전략 & 아키텍처

> 시니어 자산가 대상 유언대용신탁 특약/세금 안내 + 법률 판례 RAG 챗봇
> 최종 수정일: 2026-08-03

---

## 1. 브랜치 전략

### 1.1 브랜치 구조

```
main       ← 마일스톤(중간발표, 최종제출) 시점에만 태그, 실배포 없음
staging    ← Docker 배포 대상 브랜치
feat/*     ← 개별 기능 개발, staging 대상 PR
```

### 1.2 브랜치별 역할

| 브랜치 | 역할 | 배포 여부 | 보호 규칙 |
|---|---|---|---|
| `main` | 마일스톤 스냅샷 | 배포 없음 | staging에서만 머지, 직접 push 금지 |
| `staging` | 실제 배포 대상, 매일 작업 통합 | Docker 컨테이너 배포 | PR 리뷰 후 머지, 직접 push 금지 |
| `feat/*` | 개별 기능 개발 | - | 하루 이상 살리지 않기 |

### 1.3 브랜치 네이밍 예시

```
feat/court-precedent-mcp        # 법원 종합법률정보 API MCP 서버
feat/moleg-statute-mcp          # 법제처 법령 API MCP 서버
feat/asset-succession-simulator # 자산승계 시뮬레이터 (1~3단계 플로우)
feat/rag-citation-injection     # 판례 원문 프롬프트 주입 로직
feat/disclaimer-ui              # 정보제공 목적 고지 UI
```

### 1.4 워크플로우

```
1. feat/기능명 브랜치를 staging에서 분기
2. 작업 진행, staging → feat 수시 rebase (충돌 방지)
3. staging 대상 PR 생성 → 팀원 리뷰
4. 머지 → feat 브랜치 삭제 → Docker 이미지 빌드/배포
5. 마일스톤 시점 → staging → main 머지 + 태그
   예: git tag v0.1-중간발표
```

### 1.5 규칙

- feat 브랜치는 하루 이상 살리지 않기
- **법률 API 응답 스키마(판례/법령 데이터 구조) 변경 시 팀 채널에 공지 후 머지** — RAG 파이프라인과 FE 인용 표시 로직이 동시에 영향받음
- PR은 가능하면 `apps/web` 또는 `apps/api` 중 한쪽만 건드리도록 쪼개기
- staging, main에는 직접 push 금지

## 2. 모노레포 디렉토리 구조

```
project-root/
├── apps/
│   ├── web/                    # Next.js 프론트엔드
│   └── api/                    # FastAPI 백엔드
│
├── packages/
│   ├── rag/                    # LangChain RAG 로직
│   ├── legal-mcp/               # 법원/법제처 API 연동 MCP 서버
│   └── shared-types/           # FE/BE 공유 타입
│
├── infra/
│   ├── docker-compose.yml
│   └── nginx/
│
├── docs/
│   └── 유언대용신탁_챗봇_아키텍처.md
│
├── .github/
│   └── workflows/
│
├── turbo.json
└── README.md
```

### 2.1 설계 원칙

- **법률 MCP는 `packages/legal-mcp`로 완전히 분리** — 법원 API와 법제처 API는 인증 방식, rate limit, 응답 포맷이 서로 다르므로 각각 독립된 모듈로 관리 (세부 구조는 추후 확정)
- **RAG 체인(`packages/rag`)이 `legal-mcp`를 호출하는 구조** — 판례/법령 원문을 검색해서 가져오는 역할과, 그걸 프롬프트에 조립해 LLM에 넘기는 역할을 분리
- **disclaimer(정보제공 목적 고지)는 코드 레벨에서 강제** — 모든 체인 호출에 고정 삽입되도록 구조화 (세부 구현은 추후 확정)

## 3. RAG 아키텍처 흐름

### 3.1 전체 흐름

```
[Next.js: 사용자 질의 or 시뮬레이터 입력]
   ↓
[FastAPI Router]
   ↓
[packages/rag]
   1) 사용자 질의 임베딩 → pgvector 유사 신탁 자료 검색
   2) 질의 키워드 추출 (예: "유류분", "신탁재산 독립성")
   ↓
[packages/legal-mcp]
   3) court_precedent 클라이언트 → 법원 종합법률정보 API 호출
      → 관련 대법원/고등법원 판례 판시사항·판결요지 획득
   4) moleg_statute 클라이언트 → 법제처 API 호출
      → 민법(상속편), 신탁법 관련 최신 조문 획득
   ↓
[packages/rag/chains.py]
   5) disclaimer_prefix + 신탁 자료 + 판례 원문 + 법령 조문을
      하나의 컨텍스트로 조립하여 LLM 프롬프트에 주입
   6) LangChain chain 실행 → 답변 생성 (인용 출처 포함)
   ↓
[FastAPI] → 응답 반환 (답변 + 인용 판례/조문 메타데이터)
   ↓
[Next.js]
   - 답변 표시
   - PrecedentCard로 판례 출처(사건번호, 선고일, 법원) 별도 표시
   - DisclaimerBanner 상시 노출
```

### 3.2 왜 서버를 분리하지 않는가

- LangChain 체인, 법원/법제처 API 호출 모두 **FastAPI 프로세스 안에서 실행되는 외부 API 콜**이라 별도 서버 불필요
- 단, **법원/법제처 API가 요청 제한(rate limit)이 있는 경우** 캐싱 레이어(동일 판례/조문 재조회 방지)를 `legal-mcp` 내부에 두는 걸 권장 — 이건 서버 분리가 아니라 캐시 전략의 문제

### 3.3 판례/법령 최신성 검증 로직 (설계 시 필수 고려)

```
1) court_precedent에서 가져온 판례의 선고일 확인
2) 동일 쟁점(유류분, 신탁재산 독립성 등)에 대한 이후 판례 존재 여부 재검색
3) moleg_statute의 법령 시행일과 판례 선고일을 비교하여
   "판례 당시 적용 법령"과 "현재 시행 법령"이 다르면 UI에 경고 표시
```
이 로직이 없으면 오래된 판례를 마치 현재 유효한 법리처럼 인용할 위험이 있으므로, 초기 설계 단계부터 `PrecedentCard` 컴포넌트에 선고일/법령 시행일 병기를 반영해야 함.

## 4. Docker 배포 구성

### 4.1 apps/web/Dockerfile (Next.js)

```dockerfile
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/public ./public
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static

EXPOSE 3000
CMD ["node", "server.js"]
```

### 4.2 apps/api/Dockerfile (FastAPI)

```dockerfile
FROM python:3.11-slim AS base
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

> `packages/rag`, `packages/legal-mcp`를 참조하므로 빌드 컨텍스트는 프로젝트 루트로 잡아야 함.

### 4.3 infra/docker-compose.yml

```yaml
services:
  web:
    build:
      context: ../
      dockerfile: apps/web/Dockerfile
    ports:
      - "3000:3000"
    env_file:
      - ../apps/web/.env
    depends_on:
      - api

  api:
    build:
      context: ../
      dockerfile: apps/api/Dockerfile
    ports:
      - "8000:8000"
    env_file:
      - ../apps/api/.env
    # DB는 단일 인스턴스(Supabase 등)를 DATABASE_URL로 연결
    # 법원/법제처 API 키도 이 env_file에서 관리
```
